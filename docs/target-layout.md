# Итоговая раскладка для перекомпиляции (этап 6′, 05.11)

Решение 05.11: двоичный Z80-образ на целевую карту `refactor-plan.md` вручную
**не переносим**. При перекомпиляции Z80 → i8080 игра собирается заново из
ассемблера с метками, и раскладка получается сама. Сейчас готовим к этому
адаптер и фиксируем, куда что ляжет.

## Что сделано

- Все адреса игры и все фиксированные входы между модулями адаптера — имена
  в `cfg/labels.json` (90 меток). Из него генерируется `src/v06/labels.inc`
  (`tools/gen_labels.py`), и его включают все модули.
- Гейт `tools/test_labels.py` (в `verify_refactor`):
  - `labels.inc` совпадает с `cfg/labels.json`;
  - у каждой метки кода по её адресу лежат записанные байты (`sig`), так что
    сдвинутая процедура не вызывается по старому адресу молча;
  - в `src/v06/*.asm` нет чисел, указывающих в образ игры (3300..3F7F,
    4000..4159, 84D0..B257) или на помеченный адрес. Исключения: размерная
    арифметика `COURT_TAIL-0x3300` и MSX-адрес `0xD8EB`, который переносит
    манифест.
- Модуль-владелец метки тоже включает `labels.inc`. sjasm принимает
  повторное определение с тем же значением и падает при другом: адрес
  метки проверяется на каждой сборке.
- Замена чисел на имена не изменила образ, ROM совпал байт в байт. Попутно
  нашлись два настоящих конфликта имён: локальные `B1_COL`/`B1_ROW` в
  `win_7ae8.asm` (на деле 0F5C/0F5D, теперь `CH_COL`/`CH_ROW`) и
  `COURT_HIGH_BYTE` = 7B87 в `win_3f81.asm` (теперь `DIRTY_COURT_HIGH_BYTE`).

## Остаётся числами (сознательно)

- Рабочие ячейки адаптера 0F00..0FFF (`CSPR_*`, `B1_*`-кэш, очередь,
  клавиатура и т.п.): область принадлежит адаптеру и при перекомпиляции
  игры не двигается.
- Патчи сборщика (`tools/build_v06_rom.py`: `p.put` по адресам Z80-образа).
  Это врезки в двоичный образ; при перекомпиляции они превращаются в
  правки исходника (`JP_TAB`/`CALL_TAB`, раздел E `plan.md`).

## Карта сейчас и после перекомпиляции

| Диапазон | Сейчас | После i8080 |
|---|---|---|
| 0000..01FF | RST, BIOS-заглушки, загрузка | так же |
| 0200..0E00 | адаптер (свободно 028F..0299, 0397..040A) | так же |
| 0E00..0FFF | образ страницы 0, рабочие ячейки адаптера | так же |
| 1000..1B3F | меню LZ, хвост корта, помощники | так же |
| 1B40..1FFF | кольцо повтора | так же |
| 2000..24FF | общий графический буфер | так же |
| 2500..32FF | корт (плитки) | так же |
| 3300..3F7F | перенесённый D-блок (данные и код MSX) | данные остаются; код уходит в игру |
| 4000..4159 | рабочие ячейки игры | так же |
| 415A..6ED7 | спрайты CPC (обрезанные) | так же |
| **6ED8..775F** | **свободно 2181 Б подряд** | запас под рост кода i8080 |
| 7760..77F5 | таблица спрайтов | так же |
| 77F6..84CF | CPC-штамп, джойстик, звук, табло, помощники | так же |
| 84D0..B257 | игра Z80 (код и данные вперемешку; мёртвое обнулено) | игра i8080 из исходника с метками |
| B258..B497 | состояние, код штампа и значка | так же |
| B498..BBFF | поток спрайтов | так же |
| BC00..BFFF | стек | так же |
| C000..FFFF | видеоплоскости | так же |

Доказанно свободно сейчас 3343 Б (`classify_memory_v06`), из них 2181 Б
подряд в 6ED8..775F. Оценка роста кода при переводе на i8080 — +1,5…2 КБ
(`plan.md`, раздел C), то есть игра i8080 должна занять 84D0..B257 плюс
6ED8..775F (или вынести данные игры в свободные куски).

Бюджет `memory_budget_v06` по старой целевой карте показывает код −596 Б:
он считает окно 84D0..B257 целиком кодом. Целевые регионы бюджета
пересматриваются вместе с перекомпиляцией.
