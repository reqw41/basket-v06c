# Поле из CPC: точность и бюджет

Статический фон взят из чистого банка CPC `8B68..A567` (104 строки по 64 байта Mode 1), а не из кадра с игроками. Исходник: `src/assets/cpc_court_mode1.bin`, SHA256 `5c5f0a541dfd9a07b5f57323a4fab739bd96b78f9a53c1477dda2d43396e35d8`. Банк извлечён из `build/cpc/basket-match.ram` с SHA256 `1e0c49266142642046aa5b9e87b7640523e2f3f7deff03c8b86f2479fa0b4b07`.

Все 256×104 пикселя поля, зрителей и рекламы перенесены без изменения индексов цвета: исходные CPC pens 0/1/2/3 → Vector 0/2/1/3. Проверка независимо декодирует исходные Mode 1 bytes и сравнивает обе физические плоскости. Верхние восемь строк с щитами сохранены из прежнего фона. Палитра Vector прежняя: синий, белый, чёрный, тёплый розовый; оттенок розового ограничен аппаратной палитрой Vector.

## Память

| Ресурс | До CPC court | После tiles | После text/VECTOR |
|---|---:|---:|---:|
| Фон поля | 3584 | 3856 (213 tiles) | **3824** (211 tiles, VECTOR) |
| Сжатое меню | 2249 RLE | 1530 LZ Executive | **800** dual LZ text |
| Вместе | 5833 | 5386 | **4624** (**−762** от tiles-этапа) |

Поле: 448 индексов тайлов 8×8 + 211 тайлов по 16 байт (low/high чередуются по строкам). Основные 3584 байта остаются в `2500..32FF`; хвост 240 байт — `1600..16EF`. Три щита AMSTRAD при упаковке заменяются на VECTOR из игрового шрифта. Меню — текстовое CPC-chrome (см. [cpc-text-menu-vector.md](cpc-text-menu-vector.md)); dual LZ распаковывается в обе плоскости.

В освободившийся хвост меню входят декодер, восстановление двух цветовых плоскостей, 64-байтный кэш указателей и служебное состояние. Код нормализации порядка объектов использует в том числе бывшую процедуру отдельного восстановления high-плоскости `0B10..0B5C`; отдельный проход больше не нужен. Новых выделенных областей RAM нет, ROM сохраняет размер 65280 байт, существующие две видеоплоскости `C000..DFFF` и `E000..FFFF` остаются на месте. Это не заявка на достижение будущей целевой карты памяти: её дефицит продолжает учитываться отдельно.

## Отрисовка и регрессии

Фон восстанавливается сразу в обеих плоскостях. Для полного буфера игрока указатели тайлов готовятся только для нужных столбцов; короткий DI-only POP-копировщик читает по два байта через SP и возвращает настоящий стек.

Движок сортирует пары «игрок», «кольца», «мяч» по глубине. Полный буфер требует двух последних пар игроков: нормализатор переносит как прямоугольники, так и соответствующие staged bytes, сохраняя порядок игроков. Он учитывает мяч перед первым игроком и обрезанные позы броска, определяя игрока по высоте исходного спрайта. Высота после clipping для этого непригодна. Исключение unchanged разрешается только исходным 24-строчным кольцам. Текст HUD обновляет оба цветовых бита, чтобы смена цифр не оставляла розовые пиксели от старого символа.

Проверяются исходные пиксели меню/поля, оба сегмента банка тайлов, 672 строки SP-копировщика, 24 варианта сортировки с обрезанными позами, прозрачность и clipping, постоянство спрайтов при движении, натуральный бросок/повтор/выход из повтора, карта памяти и воспроизводимость сборки. Команда полного набора: `python3 tools/verify_refactor.py --profile full`.

Замер одного и того же keyboard-driven сценария за 500 кадров, по эмулируемому времени: прежний ROM `74a7a54e` — 6,51 обновления/с без ввода; новый фон — около 6,71. Сценарий движения и остановки — около 6,01. Это скорость логики игры, а не частота растровых кадров; разные игровые ситуации меняют стоимость кадра.
