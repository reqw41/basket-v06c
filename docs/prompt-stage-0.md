# Промпт: этап 0 с подготовленными инструментами

Работай в basket-v06c. Выполни только этап 0: зафиксируй воспроизводимую
контрольную точку перед полной перекомпоновкой памяти и четырёхцветной графикой.

Инструменты уже подготовлены:
- tools/verify_refactor.py — изолированная проверка и две чистые сборки;
- tools/test_verify_refactor.py — регрессии инструмента;
- docs/verification.md — команды, статусы и ограничения покрытия.

Не разрабатывай второй аналогичный инструмент. Не меняй игровую логику,
раскладку памяти, палитру и рендеринг на этом этапе.

1. Прочитай правила проекта и docs/verification.md. Проверь git status,
   ветку и историю. Не удаляй пользовательские изменения. Создай ветку
   refactor/memory-four-color, если её нет; существующую не перезаписывай.
   Не используй reset --hard, git clean, автоматический git add . или push.

2. Запусти из корня проекта:

   python3 tools/verify_refactor.py --profile full

   Сохрани путь к report.json/report.md. Проверь все статусы, полный хеш ROM,
   равенство двух чистых сборок сохранённому образу и целостность исходников.
   Ненулевой код не означает отсутствие отчёта: открой его и объясни причину.
   ERROR инструментария устрани. Игровые FAIL не скрывай и не исправляй
   изменением условий теста. Для подтверждения сокращённой контрольной точки
   дополнительно запусти:

   python3 tools/verify_refactor.py --profile baseline

   BASELINE_PASS не называй полной приёмкой. FAIL полного профиля допустим
   для исходной контрольной точки только с явным описанием ограничения.

3. Создай docs/refactor-baseline.md: полный хеш ROM, команды сборки,
   версии и пути зависимостей, результаты обоих профилей, ограничения,
   способы воспроизведения и расположение сохранённого эталона.
   Не полагайся на устаревшие отчёты и хеши из предыдущих сообщений.
   Укажи внешние и игнорируемые Git ресурсы, необходимые для сборки.

4. Создай docs/refactor-plan.md с этапами и целевой картой:
   0000..01FF — системные входы и загрузка;
   0200..3FFF — весь код;
   4000..4FFF — отдельный резерв 4 КБ под перекомпиляцию;
   5000..9FFF — графика, маски, шрифты, музыка;
   A000..A3FF — общий резерв 1 КБ;
   A400..AFFF — состояние и служебные данные;
   B000..B3FF — стек;
   B400..BFFF — графические буферы обеих плоскостей;
   C000..DFFF — видеоплоскость 0;
   E000..FFFF — видеоплоскость 1.

   Это бюджеты для подтверждения на этапе 1, не текущая раскладка.
   Прежнее ограничение всего кода диапазоном 84D0..B257 снимается.
   Этапы: контрольная точка → бюджет → игровые проверки → адресные
   зависимости → компактный рендеринг → ресурсы → целевая раскладка →
   четыре цвета → оптимизация → приёмка. Каждый этап — отдельный коммит.

5. Проверь состав файлов вручную. Если история ещё пуста, включи исходники
   и необходимые разрешённые ресурсы текущей игры, а также подготовленные
   инструменты проверки и документацию. Не включай кэши, секреты, посторонние
   файлы и каталоги build/verification. Сохрани эталон локально; в документации
   укажи его хеш и воспроизводимость.

6. Создай коммит:
   chore: establish reproducible refactor baseline

В конце сообщи ветку и полный хеш коммита, полный хеш ROM, пути к отчётам,
результат воспроизводимости, прошедшие и непрошедшие проверки, оставшиеся
изменения вне коммита. Не начинай этап 1 автоматически.
